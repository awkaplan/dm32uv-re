# Snake patch v11 — the "OK on SNAKE freezes the radio" root cause (found under QEMU, 2026-10-09)

Context: v7–v10 each fixed a real bug and still froze on hardware (ten restore/flash/freeze/live-RAM cycles). The radio was never crashing: it was livelocked. Found with one exec-trace histogram once the QEMU board model could reach the stock menu (see `docs/qemu-workflow.md` items 3–5 for the five emulator gaps fixed first).

## What the trace showed (r29, window after OK on SNAKE)
- 16.3M translation blocks in 10 s; `memset_bytes` 8.4M, `memcpy` 866k, `radio_telemetry_format_dispatch` @0x03011d24 826k, `strlen`/`strtol`/`vfprintf` ~1.8M, `OSFlagPost_internal` 371k, `device_telemetry_report_build` @0x03012b0c 306k, `menu_screen_render_entry_variant` @0x0303d8c8 ~13k calls, `build_sequential_index_list` ~13k calls, `main_ui_background_task_loop` spinning. I.e. Snake's category entry re-ran ~1,300 times per second forever.
- The post-mortem RAM state was CORRECT (trace markers `a1 11 01 a4 a5 a6`, count 1, array 0x030e9020, subtype 2, visible rows 1, index list built, category byte 0x0a, mode byte 0x0e) — the data was never the bug.

## Two mistakes, both in how the per-category jump tables were extended
1. The render-path table (0x030aff74, consumed by `menu_screen_render_entry_variant` @0x0303d8c8) and the item-path table (0x030aff18, consumed by `main_menu_render_and_field_edit_dispatch` @0x0303cdf0) do NOT hold functions. Their ten stock entries are addresses of CASE BLOCKS inside those two functions (render: 0x0303da4c…0x0303dd40; item: 0x0303cf1c…0x0303d54c), reached by `jmp16 a3` with the enclosing frame (`push16 l0-l2,lr; subi16 sp,4` — identical prologues at 0x0303d8c8 and 0x0303cdf0) still live. Every case ends in the shared tail at **0x0303d872**: `bsr main_menu_screen_dispatch(0x0303b6c4); addi16 sp,4; pop16 l0-l2,lr`. The item cases are literally `bsr <handler>; br32 0x0303d872`; the render cases inline the same three instructions (e.g. case 9 at 0x0303dd40: descriptor copy, `bsr build_sequential_index_list`, `bsr 0x0303b6c4`, `addi16 sp,4`, `pop16 l0-l2,lr`). v10 put plain C functions in slot 10 of both tables (`snake_category_entry` and `snake_screen_handler`); each returned through its own `pop lr`, leaving the enclosing frame unpopped on every UI pass. Only the OK-path table (0x030afef0) holds real 6-byte stubs (`bsr handler; br16 0x0303cde6`), which is why v10's OK stub was already right.
2. `snake_category_entry` called 0x03012b0c believing it was "screen_build_and_repaint". It is `device_telemetry_report_build`: category 8's contact/device-info TEXT builder (memset of a 0x154-byte buffer, strlen/memcpy, `radio_telemetry_format_dispatch`, vfprintf), which stock category 8 (`menu_contact_pick_method_option_init` @0x03043624) runs only under its `*(u8*)0x000320b0 == 1` guard and no other category runs at all. Combined with (1) it was executed ~1.3 kHz.

## The fix (v11)
- `snake_tail_stub.S`: a case-shaped stub `bsr HANDLER; lrw r3, EPILOGUE; jmp r3`, built twice by `build_tail_stub()` in `build_snake_patch.py`: render slot 10 -> 0x030e91a0 (`bsr snake_category_entry` @0x030e8400, tail 0x0303d872), item slot 10 -> 0x030e91b0 (`bsr snake_screen_handler` @0x030e8000, tail 0x0303d872). Absolute `lrw+jmp` because br16/br32 cannot reach from 0x030e9xxx.
- `snake_category_entry.c` no longer calls 0x03012b0c; it does exactly what the stock render cases do (fill count/array/subtype cells, visible-rows clamp, `build_sequential_index_list`).
- Touched sectors unchanged (0x0303c000, 0x0303d000, 0x03049000, 0x030b7000, 0x030e8000, 0x030e9000); 1,325 bytes differ from stock.

## Verified under QEMU before any flash (r30)
Image = `progmem_SNAKE_patched.bin` + ALPU-bypass sector + the two QEMU-only patches (APO off at 0x0301bde0, binding record 0x0300b10c = `ff 18 ff ff`; NEVER flash those two). `DM32_KEYSEQ` = Menu (`-1:0:1:17`), Down x10 (`2:11:1:18`), OK (`2:7:1:17`), OK. Frames: main menu with SNAKE on row 11 -> "SNAKE / [1] Play" sub-list (9,472 px) -> the game screen (snake and food drawn, OK/BACK soft keys; 641 px). Emulator still alive afterwards.

## Lessons (also in the project memory)
- Before pointing any stock jump-table slot at new code, disassemble stock entries of THAT table and look at how they end. A table that holds case blocks needs a case-shaped stub.
- Never carry a call over from another category's handler without naming what it does.
- Keypad under the model: Menu/OK = GPIOC bit 7 x GPIOB bit 17, Down = GPIOC 11 x GPIOB 18, Up = GPIOC 11 x GPIOB 17; the dedicated Up/Down injection (`-1:0:1:19/20`) does not register.

## v12-v14 (2026-10-09): making gameplay work under QEMU

The game appeared under v11 but control was impossible: arrow keys returned to the main menu instead of moving the snake. Root cause was architectural: v11's `snake_screen_handler` drew once and returned control, leaving the stock UI loop running in the same task. Stock menu keys got dispatched by stock handlers, breaking the game.

v12 restructured the handler into a blocking input loop: every 40 ms frame it scans the keypad once and latches a direction; every 6th frame (240 ms) it steps the game and redraws only the changed cells via `draw_step`. It returns only on Back.

v12's behavior under QEMU (run r35): the game ticked correctly, but the on-screen diagnostic overlay "K:xx" (scan-code readout) showed mostly 0x00 instead of the pressed keys. Execution histogram via `-d exec,nochain` + `/tmp/pchist2.py` revealed ~12k translation blocks of `keypad_poll_and_dispatch_key_event` @0x03013744 DURING the game loop, proving the stock polling task runs concurrently and is corrupting the game's own key scans.

v13 attempted to serialize both by holding the LCD/keypad bus semaphore at IRAM 0x00039344 for the whole game loop. QEMU r36 froze on the "Play" sub-list item (Stock menu still displayed; keypad reads ceased after 36 forced scans of the second OK). Root cause: confirmed by reading decompiled batch files — `OSMutexPend_wrapper2` @0x0300c500 and `OSMutexPost_wrapper2` @0x0300c53c are really `OSSemPend` and `OSSemPost` respectively; 0x00039344 is a shared semaphore taken by every LCD primitive (`display_fill_screen`, `display_fill_rect`, `display_draw_string_gb2312`, blit family, `lcd_controller_power_on_init_sequence`) AND by `keypad_poll_and_dispatch_key_event`. v13 pended it, then its first draw call pended again: self-deadlock (uC/OS-III semaphores are not recursive). The 22 batch files referencing 0x39344 are easily listed: `grep -l 39344 firmware/DM32.00.01.048/the decompiled corpus under `src/`.

v14 silences the stock poll differently. `keypad_poll_and_dispatch_key_event` @0x03013744 checks a u32 at SRAM 0x18000800 (literal pool 0x03013834). If it is 0 the poll does NOT scan; it runs a blanking stub @0x03013494 incrementing the byte at 0x0003e395 up to 0x14 (20 polls), then writes 0x18000800 = 1. v14 writes 0x18000800 = 0 and 0x0003e395 = 0 every game frame, takes the semaphore only around its own call to `keypad_scan_and_map_pressed_key` @0x03013660 (never across a draw), and on Back leaves 0x18000800 at 0 so the stock poll re-arms itself after 20 blank polls. v15 additionally waits (bounded, 50 x 20 ms) for the Back key to be released before returning, so the re-armed poll never sees that press.

Stock poll dispatch details (decompile of 0x03013744): confirmed keys (two consecutive identical scans) are stored at IRAM 0x000392c4 (current) / 0x000392c5 (previous), hold counter at 0x000392cd. Handlers are called DIRECTLY from a function-pointer table at SRAM 0x18000834 indexed by scan code. Dispatch is suppressed (except codes 3 and 6) while bit 2 of the byte at 0x0003fdb8+2 is set, and entirely (except code 6) while bit 3 of the byte at 0x0003ff84+0x2b is set — both struct owners unidentified (likely key-lock / call-active states, unverified).

`keypad_scan_and_map_pressed_key` @0x03013660 returns 0 if the 4-bit row field at GPIOB EXT_PORT bits 17..20 reads all ones; otherwise drives pins 0x47..0x4b high, returns 7 if dedicated input pin 0x34 (GPIOB bit 20) is low, 4 if pin 0x33 (GPIOB bit 19) is low, else scans 6 columns and returns `PTR_LAB_0301382c[position]` (the scan table at 0x03081f1c), or 0x65 when nothing is pressed. The dedicated Up/Down pins are only sampled when some row bit is already low.

v12's placement bug: the 1112-byte handler at 0x030e8000 overlapped `snake_category_entry` at 0x030e8400, causing a wild jump to 0x0010ec22 under QEMU. The entry moved to 0x030e8800, trampoline to 0x030e8900, and `build_snake_patch.py`'s `place()` now asserts no two blobs overlap.

Measured scan-code map (QEMU r37, all nine injected intersections matched the OpenRTX port's hardware-measured `keyMap[][]`; stock index = (GPIOC bit - 7) * 4 + (20 - GPIOB bit) into the table at 0x03081f1c): '1'=0x10 '2'=0x11 '3'=0x12 Ok=0x03 | '4'=0x13 '5'=0x14 '6'=0x15 P1=0x09 | '7'=0x16 '8'=0x17 '9'=0x18 P2=0x0c | '*'=0x0d '0'=0x0f '#'=0x0e Back=0x06 | Down=0x05 Up=0x02 (GPIOC 11). The front-panel arrows are matrix keys; the scan function's dedicated-pin early exits (codes 7/4, GPIOB bits 20/19 with every column high) are something else (side keys?) and are kept only as aliases. v11-v14's constants (OK=0x10, P1=0x11, P2=0x12, BACK=0x03) were really '1', '2', '3' and Ok. v15 controls: Up/Down arrows (or '2'/'8'), '4'/'6' or P1/P2 for left/right, Ok restarts after game over, Back exits.

v12, v13 and v14 were never flashed to hardware; only v11 was. v15's QEMU verification (run r38: four direction changes, Back, then sub-list navigation after exit) is recorded in the session notes.

### v16 (2026-10-09)

Two corrections and one constraint update:

(a) **Game state (.bss) moved from IRAM 0x00042cb1 to SRAM 0x18007000** — the IRAM slot contained kernel scalars: `OSPrioHighRdy` byte, `OSTCBHighRdyPtr` word, and neighbours. These are live objects referenced from multiple flash sites (0x0306ab04, 0x0306ad90, 0x0306aed0, 0x0306ab38, 0x0306aedc, 0x03069518, 0x0306953c) and from `OSSched` (0x00010934+) code. The 0x30f-byte game state now lives at SRAM 0x18007000 (region 0x18004c00-0x18008000 has no literal reference in flash or IRAM above 0x18004bfc, reads all-zero after a boot+menu+game session, and already hosts RAMDUMP scratch words at 0x18007FE0/0x18007FF0).

(b) **Removed 0x42c80 trace markers from `snake_category_entry.c`** — same kernel-object collision; the markers were written to confirm state but the address overlapped `OSPrioHighRdy` and neighbours.

(c) **QEMU hangs (r38, r40, r41, r43) attributed to the stock-reproducible emulator crash** described in `docs/qemu-workflow.md` section 6 (random scheduler livelock after 15 s to minutes, stock firmware, reproduce-independent of the patch). The remaining v15/v16 hangs all carry that crash signature (`pc=0x00000000`, `epc` in `OSSched`). These are NOT attributed to the patch; rather, the emulator defect prevents full v16 validation under QEMU.

(d) **(superseded by v21 below; the emulator defect is fixed, see DM32-BOARD-MODEL.md section 6.)** v16 was the candidate at the time, but Back-exit verification was incomplete. The game gameplay path, direction input path, and forward geometry are verified end-to-end under QEMU (r37 measured against the hardware-confirmed OpenRTX keypad map and all nine test vectors matched). The Back-exit path has NOT been cleanly verified under QEMU because of the emulator defect mentioned above. **v12-v16 have never been flashed to hardware.**

### v17-v21 (2026-10-10): the exit path

Why Back needed extra presses before v21: entering "Play" through the stock item-OK path pushes one UI level -- diff of the fresh sub-list state (r60) against the state right after the game returned (r68): `dialog_history_ui_state` @0x000320ac bytes +0..+3 02 02 03 0e -> 03 03 04 15, byte 0x0003e8ec 2 -> 3, byte 0x0003e909 0 -> 1, and active_visible_rows (0x0003e8f4) zeroed. The item epilogue (tail 0x0303d872 -> main_menu_screen_dispatch) then redraws only the list body, without the title (non-black 9158 vs 9472), and the stock needs a Back of its own to pop the level. Attempts that did NOT work: v17 (wait for release, then 0x18000800 = 1 + re-run snake_category_entry: UI alive again but two extra Backs), v18 (re-enable the poll while Back is still held), v19 (call the stock Back handler's primitive `write_field_and_mbox_post(2, 6)` @0x03013178 before returning -- the event is discarded on the way out of the dispatcher), v20 (set cur/prev with the poll enabled -- also lost under the epilogue). v21 defers the dispatch to the stock poll ~200 ms after the return, which is what the r62/r64 second-Back presses had been doing by hand. Staged for hardware: `/tmp/snake_v21/` (the six sectors + MANIFEST.sha256, byte-identical to the r69 image minus the three QEMU-only patches). v12-v21 have NOT been flashed; v11 is still on the radio.

Stock keypad poll remained disabled forever after Back (v14-v16 left counter 0x0003e395 stuck at 0, u32 0x18000800 stuck at 0, UI deaf). Root cause: the blanking stub @0x03013494 re-arms keypad only while the u32 at 0x00030790 is non-zero; stub returns immediately if it is zero, never re-enabling. **Fixes (v21, tested r69):** on Back the game sets 0x00030790 = 1, counter 0x0003e395 = 0, 0x18000800 = 0 (re-arm gate) BEFORE returning (cells already restored via snake_category_entry). Stock blanking stub counts 20 polls (~200 ms, after epilogue finishes) and re-enables keypad; first real poll sees the confirmed-key cells cur (0x000392c4) = 6, prev (0x000392c5) = 0 (written by the game's Back branch), dispatches handler[6] = stock Back, pops the pushed UI level and redraws with title. Verified sequence (r69): four direction changes, one Back → sub-list with title, Back → main menu SNAKE highlighted, Down → Talk Group, Back → standby. Key facts: (a) 0x00030790 at 0x030388+0x408 MUST be non-zero for the re-arm to fire; (b) confirmed-key cells at 0x000392c4/0x000392c5 (cur/prev) + dispatch rule: cur != prev && cur != 0 → handler[cur] at table 0x18000834[cur]; prev = cur after; (c) key events posted from inside dispatcher are discarded before UI processes them. **v21 was flashed to the radio on 2026-10-10 and failed on hardware for the reason documented in v22 below.** The image at `/tmp/snake_v21/` (six sectors + MANIFEST.sha256) is no longer a candidate.

### v22 (2026-10-10): the LCD data bus is the keypad row bus

The game screen appeared once after v21 flashed, then froze — no snake movement, no "K:xx" readout, background white, and after Back the stock screens stayed white until power cycle. **Root cause:** `keypad_scan_and_map_pressed_key` @0x03013660 calls `rf_modem_mute_during_keypad_scan` @0x03012e14 (now named `keypad_scan_begin_mux_rows_drive_low`; there is no modem mute), which writes `IO_DIPLEX2 |= 0xfe00` (SystemControl 0x11000000+0x3c) to hand GPIO pads 0x47..0x4b (GPIOC 7..11) to the keypad matrix. These pads are the LCD data bus DB0..DB4. Stock's poll restores them immediately after (`0x0301cad0` writes `IO_DIPLEX2 &= 0xffff01ff`); stock's display pipeline restores them before clearing the screen (mask 0xfff80107 in `lcd_controller_power_on_init_sequence` @0x03017d4c). v21 called the scan every 40 ms and never restored, so after the first scan every LCD data write hit GPIO pins instead of the panel — the frame froze at the first scan. **Fix in v22:** call 0x0301cad0 right after every scan, still inside the semaphore hold (macro `lcd_bus_restore_after_keypad_scan` in `snake_ui.h`). Verified under QEMU (run r71): gameplay, Back to sub-list with title, Back to main menu, Down, Back to standby — all with correct graphics. Staged at `/tmp/snake_v22/` (six sectors + MANIFEST.sha256); only sector 0x030e8000 differs from v21.

### Review notes (2026-10-10, after v22)

Corrections to statements above, checked against the stock image and under the fixed emulator (details and evidence in `docs/patch-patterns.md` section 10):

- **v16(a), which kernel objects.** The old `.bss` (linked at `0x00042cb4`) did not cover `OSPrioHighRdy`/`OSTCBHighRdyPtr`; those sit just below, at `0x00042ca8`/`0x00042cac`. It covered kernel words `0x42cb4..0x42cc8` (statistics-task counters, and `0x42cc0`, which IRAM scheduler code reads at `0x10b08`). The move to SRAM was still right.
- **v16(c), the r38 hang.** Rebuilt with `.bss 0x00042cb1` and run under the fixed emulator (image `dm32uv-re-pipeline:qemufix3`), the game ran 260 s with 27 direction changes, then another 120 s with `len` forced to 12 so the body array overwrote `0x42cc0..`, without a crash. That supports v16(c)'s attribution of r38 to the emulator PSR bug over `snake_game.ld`'s attribution to the collision. A run of the exact v15 sources would settle it.
- **v14 / v21, the re-arm gate.** The blanking stub re-enables the poll on the 21st blank poll (counter > `0x14`) and then **clears** `0x00030790`, so that word is a one-shot "re-enable later" request; `0x18000800` is the enable word itself (v21's "0x18000800 = 0 (re-arm gate)" mislabels it). Stock uses the same idiom (`0x03059550`, `0x03022fac`: `0x18000800 = 0; 0x00030790 = 1`).
- **v12, which task.** The poll does not run in the game's task. Under QEMU with gdb breakpoints the game's scan ran in "task menu" (TCB `0x0003e4fc`) and the poll in "task init" (TCB `0x00040da0`), which is why parking it every frame was needed.
- **v11 Lessons, "dedicated Up/Down injection".** `-1:0:1:19/20` forces the scan's dedicated-pin exits (codes 4/7), which are not the arrows; the arrows are matrix keys `2:11:1:17` / `2:11:1:18`.
